Módulo 5: CI/CD com GitHub Actions

Como usar

Módulo 5: do commit à produção

Cada mudança passa sozinha por testes, verificações de segurança e chega à produção sem passos manuais. Este módulo cobre a seção de CI/CD do roadmap DevOps usando GitHub Actions.

  1. Crie um repositório de testes no GitHub
  2. Abra os tópicos em ordem
  3. Escreva cada workflow, faça push e acompanhe na aba Actions
  4. Quebre o pipeline de propósito para ver como ele falha

5A. Conceitos · Tópico 1

CI, CD e métricas DORA

O que estudar

  • Integração contínua: integrar na main várias vezes ao dia, com build e testes automáticos
  • Continuous Delivery vs Continuous Deployment: aprovação manual no fim ou não
  • Estágios típicos: lint, testes, build, scans, publicação do artefato, deploy, verificação
  • Artefato imutável: construir uma vez e promover a mesma imagem entre ambientes
  • Pipeline como código versionado com a aplicação
  • Métricas DORA: frequência de deploy, lead time, taxa de falha e tempo de recuperação
  • Ferramentas do mercado: GitHub Actions, GitLab CI, Jenkins, CircleCI, Argo CD
push → lint → testes → SAST/SCA → build → scan → push da imagem → deploy staging → testes → aprovação → produção → smoke test

5A. Conceitos · Tópico 2

Anatomia de um workflow

O que estudar

  • Arquivo YAML em .github/workflows/ e sintaxe YAML (indentação, listas, mapas)
  • Hierarquia: workflow → jobs → steps
  • Runners: GitHub-hosted (ubuntu-latest) vs self-hosted
  • Steps: run (comando) vs uses (action), with para entradas
  • env no nível do workflow, job e step
  • permissions do GITHUB_TOKEN
  • Ler os logs e reexecutar jobs
name: ci on: [push] permissions: contents: read jobs: ola: runs-on: ubuntu-latest env: AMBIENTE: dev steps: - uses: actions/checkout@v4 - name: Informações run: | echo "Commit ${{ github.sha }} por ${{ github.actor }}" echo "Ambiente: $AMBIENTE"

5A. Conceitos · Tópico 3

Eventos, expressões e contextos

O que estudar

  • Eventos: push, pull_request, workflow_dispatch (com inputs), schedule, release, workflow_run
  • Filtros: branches, tags, paths
  • Contextos: github, env, vars, secrets, matrix, needs, steps, runner
  • Expressões: ${{ }}, if:, operadores e funções (contains, startsWith, success, failure, always)
  • Outputs de steps com $GITHUB_OUTPUT
  • concurrency: cancelar execuções antigas da mesma branch
on: pull_request: paths: ["app/**", "Dockerfile"] workflow_dispatch: inputs: ambiente: { type: choice, options: [staging, prod] } concurrency: group: ${{ github.workflow }}-${{ github.ref }} cancel-in-progress: true jobs: x: if: github.actor != 'dependabot[bot]' steps: - id: v run: echo "tag=$(date +%Y%m%d)-${GITHUB_SHA::7}" >> "$GITHUB_OUTPUT" - run: echo "${{ steps.v.outputs.tag }}"

5B. Integração contínua · Tópico 4

Testes e qualidade

O que estudar

  • Pirâmide de testes: unitários, integração, ponta a ponta
  • Lint e formatação (eslint, ruff, gofmt) como primeiro passo
  • Cobertura de testes e relatórios
  • Serviços no job: subir PostgreSQL para testes de integração
  • Branch protection: status checks obrigatórios
  • Feedback rápido: mirar menos de 10 minutos
jobs: test: runs-on: ubuntu-latest services: postgres: image: postgres:16 env: { POSTGRES_PASSWORD: test } ports: ["5432:5432"] options: --health-cmd pg_isready --health-interval 5s steps: - uses: actions/checkout@v4 - uses: actions/setup-python@v5 with: { python-version: "3.12", cache: pip } - run: pip install -r requirements.txt - run: ruff check . - run: pytest --cov=app env: { DATABASE_URL: postgresql://postgres:test@localhost/postgres }

5B. Integração contínua · Tópico 5

Jobs, needs e artifacts

O que estudar

  • Paralelismo por padrão e ordem com needs
  • Outputs entre jobs via needs.job.outputs
  • Artifacts: upload e download, retenção
  • Condições: rodar deploy só na main, só se testes passarem
  • timeout-minutes e continue-on-error
  • Job summaries com $GITHUB_STEP_SUMMARY
jobs: build: outputs: versao: ${{ steps.v.outputs.versao }} steps: - id: v run: echo "versao=1.4.${{ github.run_number }}" >> "$GITHUB_OUTPUT" - run: npm run build - uses: actions/upload-artifact@v4 with: { name: dist, path: dist/, retention-days: 7 } deploy: needs: build if: github.ref == 'refs/heads/main' timeout-minutes: 15 steps: - uses: actions/download-artifact@v4 with: { name: dist } - run: echo "Versão ${{ needs.build.outputs.versao }}" >> "$GITHUB_STEP_SUMMARY"

Cache, matrix e reuso

O que estudar

  • Cache de dependências: embutido nos setup-* ou actions/cache com chave por hash do lockfile
  • Cache de camadas Docker (type=gha)
  • Matrix: várias versões e sistemas, include, exclude, fail-fast
  • Reusable workflows: workflow_call para padronizar pipelines entre repositórios
  • Composite actions: agrupar steps repetidos
  • Custos e limites de minutos dos runners
strategy: fail-fast: false matrix: os: [ubuntu-latest, windows-latest] node: [20, 22] # reuso: .github/workflows/ci-reutilizavel.yml on: workflow_call: inputs: node: { type: string, default: "20" } # chamando em outro workflow jobs: ci: uses: voce/pipelines/.github/workflows/ci-reutilizavel.yml@v1 with: { node: "22" }

5C. Entrega contínua · Tópico 7

Secrets e variables

O que estudar

  • Níveis: repositório, environment, organização
  • Secrets vs variables: sensível e mascarado vs configuração comum
  • GITHUB_TOKEN: token automático e o bloco permissions
  • Mascaramento e o risco de imprimir segredos derivados
  • PRs de forks não recebem secrets (e o perigo do pull_request_target)
  • Gerenciadores externos: AWS Secrets Manager, Vault, buscados em tempo de execução
gh secret set SLACK_WEBHOOK gh secret set DB_PASSWORD --env production gh variable set AWS_REGION --body us-east-1 steps: - run: ./notificar.sh env: WEBHOOK: ${{ secrets.SLACK_WEBHOOK }} REGIAO: ${{ vars.AWS_REGION }}
Secrets em variáveis de ambiente do step, nunca interpolados direto no script com ${{ }} (evita injeção).

Build e publicação de imagens

O que estudar

  • Buildx e build-push-action
  • Login: GHCR com GITHUB_TOKEN, ECR via OIDC
  • Tags automáticas com docker/metadata-action (SHA, branch, semver)
  • Cache de camadas no GitHub Actions
  • Builds multiplataforma (amd64 e arm64)
  • Releases: tags git disparando versões
permissions: { contents: read, packages: write } steps: - uses: docker/setup-buildx-action@v3 - uses: docker/login-action@v3 with: registry: ghcr.io username: ${{ github.actor }} password: ${{ secrets.GITHUB_TOKEN }} - id: meta uses: docker/metadata-action@v5 with: images: ghcr.io/${{ github.repository }} tags: | type=sha type=semver,pattern={{version}} - uses: docker/build-push-action@v6 with: push: true tags: ${{ steps.meta.outputs.tags }} cache-from: type=gha cache-to: type=gha,mode=max

5D. Deploy · Tópico 10

OIDC com a AWS

O GitHub prova sua identidade para a AWS e recebe credenciais temporárias. Nenhuma access key fica guardada.

O que estudar

  • Como funciona: token OIDC do GitHub, Identity Provider no IAM, AssumeRoleWithWebIdentity
  • Trust policy: condição no campo sub restringindo repositório, branch ou environment
  • Permissions: id-token: write
  • Role mínima por finalidade (deploy, terraform plan, terraform apply)
  • Mesma ideia em outras nuvens e na Cloudflare (tokens com escopo)
"Condition": { "StringEquals": {"token.actions.githubusercontent.com:aud": "sts.amazonaws.com"}, "StringLike": {"token.actions.githubusercontent.com:sub": "repo:voce/projeto:environment:production"} } # workflow permissions: { id-token: write, contents: read } - uses: aws-actions/configure-aws-credentials@v4 with: role-to-assume: arn:aws:iam::123456789012:role/gh-deploy aws-region: us-east-1

5D. Deploy · Tópico 11

Estratégias de deploy

O que estudar

  • Recreate: derruba e sobe (tem indisponibilidade)
  • Rolling update: troca instâncias aos poucos
  • Blue/green: dois ambientes, troca o tráfego de uma vez
  • Canary: pequena porcentagem do tráfego primeiro
  • Mecanismos na AWS: SSM Run Command na EC2, nova task definition no ECS, CodeDeploy
  • Migrações de banco compatíveis com versões antiga e nova
  • Smoke test e health check depois do deploy
- name: Deploy no ECS uses: aws-actions/amazon-ecs-deploy-task-definition@v2 with: task-definition: task.json service: api cluster: prod wait-for-service-stability: true - name: Smoke test run: | for i in $(seq 1 10); do curl -fsS https://meu-app.com/health && exit 0; sleep 6 done; exit 1

5D. Deploy · Tópico 12

Rollback, notificações e GitOps

O que estudar

  • Rollback: redeploy da tag anterior, rollback automático quando o smoke test falha
  • Notificações: Slack, Teams ou e-mail com status e link do run
  • Observabilidade do pipeline: duração, taxa de falha
  • GitOps (visão geral): o estado desejado no Git e um agente (Argo CD, Flux) sincroniza o cluster
  • Push vs pull deploy
- name: Rollback automático if: failure() run: ./deploy.sh prod "${{ vars.ULTIMA_TAG_ESTAVEL }}" - name: Notificar if: always() env: { WEBHOOK: "${{ secrets.SLACK_WEBHOOK }}" } run: | curl -s -X POST -H 'Content-type: application/json' \ --data "{\"text\":\"Deploy ${{ job.status }}: ${{ github.server_url }}/${{ github.repository }}/actions/runs/${{ github.run_id }}\"}" \ "$WEBHOOK"

DevSecOps

Pipeline seguro

O que estudar e aplicar

  1. SAST: CodeQL ou Semgrep no código
  2. SCA: Dependabot, Trivy fs, npm audit para dependências
  3. Secret scanning: gitleaks e push protection do GitHub
  4. IaC scan: Checkov ou Trivy config (módulo 6)
  5. Container scan: Trivy na imagem, falhando em CRITICAL
  6. DAST: OWASP ZAP baseline contra staging
  7. Cadeia de suprimentos: actions fixadas por SHA, SBOM, assinatura com cosign, attestations
  8. Hardening: permissions mínimas, cuidado com pull_request_target e injeção via títulos de PR
  9. OIDC no lugar de chaves
- uses: github/codeql-action/init@v3 with: { languages: python } - uses: github/codeql-action/analyze@v3 - uses: gitleaks/gitleaks-action@v2 - uses: aquasecurity/trivy-action@0.28.0 with: image-ref: ghcr.io/voce/app:${{ github.sha }} severity: CRITICAL,HIGH exit-code: "1" - uses: zaproxy/action-baseline@v0.14.0 with: { target: "https://staging.meu-app.com" }
