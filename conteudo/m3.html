3A. Conceitos · Tópico 1

Containers vs VMs

Uma VM virtualiza hardware e roda um sistema operacional completo. Um container é um processo isolado que compartilha o kernel do host, por isso sobe em segundos e ocupa megabytes.

O que estudar

  • Problema que containers resolvem: "na minha máquina funciona", dependências conflitantes, ambientes diferentes
  • Bare metal vs VMs vs containers: isolamento, desempenho, densidade
  • Tecnologias do kernel: namespaces (pid, net, mnt, uts, user) isolam; cgroups limitam CPU e memória; union filesystem (overlay2) empilha camadas
  • Imagem vs container: modelo somente leitura vs instância em execução com camada gravável
  • Padrão OCI e alternativas: Podman, containerd
Container não é segurança total: o kernel é compartilhado. Por isso hardening de containers importa (veja DevSecOps).

3A. Conceitos · Tópico 2

Como o Docker funciona

O que estudar

  • Arquitetura cliente-servidor: docker CLI fala com o daemon dockerd via API (socket /var/run/docker.sock)
  • Componentes: dockerd, containerd, runc
  • Objetos: imagens, containers, volumes, redes
  • Registry: Docker Hub, Amazon ECR, GitHub Container Registry
  • Instalação: Docker Engine no Linux, Docker Desktop no Windows e macOS
  • Modo rootless (conceito)
curl -fsSL https://get.docker.com | sh sudo usermod -aG docker $USER # depois faça logout e login docker version # cliente e servidor docker info # driver de storage, nº de containers docker run --rm hello-world
Quem acessa o docker.sock tem poder de root no host. Nunca monte o socket dentro de containers sem necessidade real.

Ciclo de vida e CLI

O que estudar

  • Estados: created, running, paused, exited
  • Executar: run com -d, --name, -p, -e, --rm, -it
  • Inspecionar: ps, logs, inspect, stats, top
  • Entrar no container: exec -it sh ou bash
  • Controlar: stop, start, restart, kill, rm
  • Políticas de restart: no, on-failure, unless-stopped, always
  • Limpeza: system df, system prune, image prune
docker run -d --name web -p 8080:80 --restart unless-stopped nginx:1.27 docker ps ; docker ps -a docker logs -f --tail 50 web docker exec -it web sh docker inspect web | jq '.[0].NetworkSettings.IPAddress' docker stats --no-stream docker stop web && docker rm web docker system df ; docker system prune

3B. Imagens · Tópico 4

Dockerfile

A receita da imagem. Cada instrução é um passo do build.

O que estudar

  • Instruções: FROM, WORKDIR, COPY vs ADD, RUN, ENV, ARG, EXPOSE, USER, CMD vs ENTRYPOINT, HEALTHCHECK, LABEL
  • Contexto de build e o arquivo .dockerignore
  • Forma exec vs shell: CMD ["node","app.js"] vs CMD node app.js (sinais e PID 1)
  • ARG em build vs ENV em runtime
  • docker build com -t, -f, --build-arg, --no-cache
  • BuildKit e buildx para builds multiplataforma (amd64 e arm64)
FROM python:3.12-slim WORKDIR /app ENV PYTHONUNBUFFERED=1 COPY requirements.txt . RUN pip install --no-cache-dir -r requirements.txt COPY . . RUN useradd -r app && chown -R app /app USER app EXPOSE 8000 HEALTHCHECK CMD python -c "import urllib.request;urllib.request.urlopen('http://localhost:8000/health')" CMD ["uvicorn", "main:app", "--host", "0.0.0.0"]

3B. Imagens · Tópico 5

Camadas, cache e tamanho

Imagens menores sobem mais rápido, custam menos e têm menos vulnerabilidades.

O que estudar

  • Camadas: cada RUN, COPY e ADD cria uma camada imutável
  • Cache: ordem das instruções (dependências antes do código)
  • Imagens base: full vs slim vs alpine vs distroless vs scratch
  • Multi-stage builds: compilar numa etapa, copiar só o binário para a final
  • Limpeza no mesmo RUN: apt-get clean, rm -rf /var/lib/apt/lists/*
  • Analisar: docker history e a ferramenta dive
FROM node:20-alpine AS build WORKDIR /src COPY package*.json ./ RUN npm ci COPY . . RUN npm run build && npm prune --omit=dev FROM gcr.io/distroless/nodejs20-debian12 COPY --from=build /src/dist /app/dist COPY --from=build /src/node_modules /app/node_modules USER nonroot CMD ["/app/dist/index.js"]

3B. Imagens · Tópico 6

Registries e tags

O que estudar

  • Nome completo: registry/namespace/repositório:tag
  • Registries: Docker Hub, Amazon ECR, GitHub Container Registry (ghcr.io), privados
  • Estratégia de tags: versão semântica (1.4.2), SHA do commit, por que evitar latest em produção
  • Digest: referência imutável @sha256:...
  • Login, push, pull e credential helpers
  • Retenção: políticas de lifecycle no ECR
docker tag minha-api:dev ghcr.io/voce/minha-api:1.0.0 echo $GH_TOKEN | docker login ghcr.io -u voce --password-stdin docker push ghcr.io/voce/minha-api:1.0.0 aws ecr get-login-password | docker login --username AWS \ --password-stdin 123456789012.dkr.ecr.us-east-1.amazonaws.com docker pull nginx@sha256:abc... # versão exata

3C. Dados e rede · Tópico 7

Volumes e persistência

Containers são descartáveis: tudo escrito na camada gravável some ao remover o container.

O que estudar

  • Volumes nomeados: gerenciados pelo Docker, ideais para bancos
  • Bind mounts: pasta do host, ideal para desenvolvimento
  • tmpfs: dados em memória
  • Somente leitura: :ro e --read-only
  • Backup e restore de volumes
  • Permissões entre UID do container e do host
docker volume create pgdata docker run -d --name db -v pgdata:/var/lib/postgresql/data \ -e POSTGRES_PASSWORD_FILE=/run/secrets/pg postgres:16 docker run -v "$(pwd)/src:/app/src:ro" minha-api:dev # backup do volume docker run --rm -v pgdata:/dados -v "$(pwd)":/bkp alpine \ tar czf /bkp/pgdata.tgz -C /dados .

3C. Dados e rede · Tópico 8

Redes do Docker

O que estudar

  • Drivers: bridge (padrão), host, none, overlay (Swarm)
  • Rede bridge customizada: DNS interno, containers se acham pelo nome
  • Publicação de portas: -p host:container e o bind em 127.0.0.1
  • Isolamento: separar front e back em redes diferentes
  • Como o Docker mexe no iptables e por que isso pode furar o ufw
  • Proxy reverso com Nginx ou Traefik na frente dos containers
docker network create back docker run -d --name db --network back postgres:16 docker run -d --name api --network back -p 127.0.0.1:8000:8000 minha-api docker exec api getent hosts db # resolve pelo nome docker network inspect back
Portas publicadas com -p ignoram regras do ufw. Para serviços internos, publique em 127.0.0.1 ou não publique.

3C. Dados e rede · Tópico 9

Configuração e recursos

O que estudar

  • 12 Factor: configuração por variáveis de ambiente, mesma imagem em todos os ambientes
  • -e, --env-file e precedência
  • Segredos: arquivos montados (/run/secrets) em vez de variáveis quando possível
  • Limites: --memory, --cpus, --pids-limit
  • OOM: o que acontece quando o container estoura a memória
  • Sinais e graceful shutdown: SIGTERM, --stop-timeout, init (--init ou tini)
docker run -d --env-file .env \ --memory 512m --cpus 1 --pids-limit 200 \ --init --stop-timeout 20 minha-api:1.0.0 docker inspect --format '{{.State.OOMKilled}}' api

3D. Compose e operação · Tópico 10

compose.yaml

O Compose descreve uma aplicação de vários containers como código.

O que estudar

  • Estrutura: services, networks, volumes, secrets
  • build vs image
  • ports, environment, env_file e interpolação ${VAR}
  • Override files: compose.override.yaml para dev
  • Profiles para serviços opcionais
services: proxy: image: nginx:1.27-alpine ports: ["80:80"] volumes: ["./nginx.conf:/etc/nginx/conf.d/default.conf:ro"] networks: [front] api: build: . env_file: .env networks: [front, back] db: image: postgres:16 environment: POSTGRES_PASSWORD_FILE: /run/secrets/db_pass secrets: [db_pass] volumes: [pgdata:/var/lib/postgresql/data] networks: [back] networks: { front: {}, back: {} } volumes: { pgdata: {} } secrets: db_pass: { file: ./secrets/db_pass.txt }

Saúde e dependências

O que estudar

  • healthcheck: test, interval, timeout, retries, start_period
  • depends_on com condition: service_healthy e service_completed_successfully
  • restart no Compose
  • Containers de migração que rodam e terminam antes da API
  • Comandos: up -d --build, ps, logs -f, exec, down, down -v (apaga volumes!)
db: healthcheck: test: ["CMD-SHELL", "pg_isready -U postgres"] interval: 5s retries: 10 migrate: build: . command: ["npm", "run", "migrate"] depends_on: { db: { condition: service_healthy } } api: depends_on: migrate: { condition: service_completed_successfully } restart: unless-stopped

Logs, debug e orquestração

O que estudar

  • Logs: stdout e stderr, drivers json-file, awslogs, rotação com max-size
  • Debug: logs, inspect, exec, docker events, container de debug com a mesma rede
  • Problemas comuns: container sai na hora (PID 1 terminou), porta ocupada, permissão em volume, OOM
  • Desenvolvimento: hot reload com bind mount e compose watch
  • Orquestração (visão geral): por que Kubernetes, ECS e Docker Swarm existem: escala, autocura, rolling update
docker run --log-opt max-size=10m --log-opt max-file=3 ... docker logs api 2>&1 | grep -i error docker events --since 10m docker run --rm -it --network container:api nicolaka/netshoot docker compose watch
Você vai usar o driver awslogs no projeto final para mandar os logs ao CloudWatch.

DevSecOps

Containers seguros

O que estudar e aplicar

  1. Imagem base confiável: oficial, mínima, com tag fixa ou digest, atualizada com frequência
  2. Usuário não root e --cap-drop ALL, adicionando só o necessário
  3. Sistema de arquivos somente leitura (--read-only + tmpfs)
  4. no-new-privileges e nunca --privileged
  5. Scan de vulnerabilidades (Trivy, Docker Scout) e falhar o build em CRITICAL
  6. Lint do Dockerfile com hadolint
  7. SBOM: lista de componentes da imagem
  8. Assinatura de imagens com cosign (conceito)
  9. Segredos: nunca em ENV, ARG ou COPY; use secrets do Compose ou do orquestrador
  10. CIS Docker Benchmark com docker-bench-security
hadolint Dockerfile trivy image --severity HIGH,CRITICAL --exit-code 1 minha-api:1.0.0 trivy image --format cyclonedx -o sbom.json minha-api:1.0.0 docker run --read-only --tmpfs /tmp --cap-drop ALL \ --security-opt no-new-privileges minha-api:1.0.0

Projeto prático

Aplicação completa em containers

  1. API simples (Node, Python ou Go) com /health e logs em JSON
  2. Dockerfile multi-stage, imagem final distroless ou slim, usuário não root, abaixo de 150 MB
  3. compose.yaml com Nginx (proxy), API, PostgreSQL e um serviço de migração
  4. Redes front e back separadas, banco sem porta publicada
  5. Healthchecks e depends_on com condição
  6. Senha do banco via secrets, nada no .env versionado
  7. hadolint e Trivy sem falhas críticas, SBOM gerado
  8. Imagem publicada no GHCR ou Docker Hub com tag semântica
