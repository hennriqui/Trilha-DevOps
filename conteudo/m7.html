Módulo 7: Projeto Final

Como usar

Projeto final de ponta a ponta

Aqui você junta tudo: aplicação em containers, publicada na AWS com Terraform, protegida na borda pela Cloudflare, com deploy automático e seguro pelo GitHub Actions e monitorada no CloudWatch.

usuário → Cloudflare (DNS, WAF, TLS) → ALB (HTTPS, subnet pública) → ECS Fargate ou EC2 (subnet privada) → RDS PostgreSQL (subnet de dados) dev → PR (testes + scans + terraform plan) → merge → build + Trivy → ECR → deploy via OIDC → smoke test → CloudWatch Logs + métricas + alarmes → SNS
Faça cada etapa num Pull Request separado. O histórico do repositório vira a história do projeto para recrutadores.

Etapa 1. Aplicação · Tarefa 1

Aplicação e requisitos

Escolha algo pequeno para que o foco fique na operação: uma API de tarefas, encurtador de links ou catálogo, com banco PostgreSQL.

O que entregar

  • Endpoints: CRUD básico, GET /health (liveness) e GET /ready (verifica o banco)
  • Configuração por variáveis de ambiente (12 Factor)
  • Logs estruturados em JSON com nível, mensagem, caminho e tempo de resposta
  • Graceful shutdown ao receber SIGTERM
  • Migrações de banco versionadas
  • Requisitos não funcionais escritos: disponibilidade alvo, latência, custo máximo mensal

Dockerfile de produção

Critérios

  • Multi-stage, imagem final slim ou distroless com tag fixa
  • Usuário não root e forma exec no CMD
  • HEALTHCHECK no /health

Etapa 3. Infra com Terraform · Tarefa 5

Rede e borda

Critérios

  • Módulo network: VPC /16, subnets públicas, privadas e de dados em 2 AZs, IGW, rotas, NAT (ou VPC endpoints para economizar)
  • Security Groups em camadas: ALB 443 da internet, app só do ALB, banco só da app
  • ALB com certificado do ACM e redirecionamento de 80 para 443
  • Cloudflare (opcional): registro DNS com proxy, SSL Full (strict), WAF gerenciado, SG do ALB aceitando só IPs da Cloudflare
  • Flow logs da VPC ligados
Sem porta 22 aberta em lugar nenhum. Acesso administrativo só por Session Manager.

Etapa 3. Infra com Terraform · Tarefa 6

Computação, dados e registry

Critérios

  • ECR com scan on push, tags imutáveis e lifecycle policy
  • Computação: ECS Fargate (recomendado) com 2 tarefas em AZs diferentes, ou EC2 em Auto Scaling Group na subnet privada
  • Task role e execution role com permissões mínimas
  • RDS PostgreSQL criptografado, backups automáticos, sem acesso público
  • Senha gerada com random_password, guardada no Secrets Manager e injetada como secret na task
  • Outputs: URL da aplicação, endpoint do banco, nome do repositório ECR
cd infra/envs/prod terraform init && terraform plan -out=tfplan terraform apply tfplan terraform output -raw app_url

Etapa 4. CI/CD · Tarefa 8

Pipeline de PR

pr.yml em pull_request. Tudo precisa passar para liberar o merge.

Critérios

  1. Lint e testes com PostgreSQL como service container
  2. CodeQL ou Semgrep (SAST)
  3. gitleaks (segredos) e Trivy fs (dependências)
  4. hadolint no Dockerfile
  5. terraform fmt -check, validate, tflint, Checkov e plan publicado como comentário
  6. permissions mínimas e actions fixadas por versão ou SHA
  7. concurrency cancelando execuções antigas

Etapa 4. CI/CD · Tarefa 9

Build e publicação

main.yml no push para main.

Critérios

  • Credenciais AWS via OIDC (role só com push no ECR)
  • Tags com metadata-action: SHA do commit e versão semântica nas releases
  • Cache de camadas type=gha
  • Trivy na imagem bloqueando CRITICAL antes do push
  • SBOM anexado ao run e, opcional, assinatura com cosign
- uses: aws-actions/configure-aws-credentials@v4 with: { role-to-assume: "${{ vars.ROLE_BUILD }}", aws-region: us-east-1 } - uses: aws-actions/amazon-ecr-login@v2 - uses: docker/build-push-action@v6 with: push: true tags: ${{ vars.ECR_REPO }}:${{ github.sha }} cache-from: type=gha cache-to: type=gha,mode=max

Etapa 4. CI/CD · Tarefa 10

Deploy seguro

Critérios

  1. OIDC provider e roles criados pelo Terraform, trust policy restrita ao repositório e ao environment
  2. Deploy automático em dev; produção com environment protegido e aprovação
  3. Rolling update no ECS com wait-for-service-stability
  4. Migrações rodando antes da nova versão
  5. Smoke test no /health e /ready com retentativas
  6. Rollback automático para a tag anterior se falhar
  7. Notificação do resultado com link do run
  8. Opcional: OWASP ZAP baseline contra dev
Critério de aceite: nenhuma access key da AWS guardada em secrets do GitHub.

Etapa 5. Observabilidade · Tarefa 11

Logs centralizados

Critérios

  • Driver awslogs na task do ECS (ou CloudWatch Agent na EC2)
  • Log group por serviço com retenção definida, criado no Terraform
  • Logs em JSON com request id para rastrear uma requisição
  • Consultas salvas no Logs Insights: erros por rota, latência p95
  • Logs do ALB enviados ao S3
  • CloudTrail ativo para auditoria da conta
fields @timestamp, level, path, duration_ms | filter level = "error" | stats count() as erros by path | sort erros desc stats pct(duration_ms, 95) as p95 by bin(5m)

Etapa 5. Observabilidade · Tarefa 12

Métricas, alarmes e SLOs

Critérios

  • SLO definido: por exemplo 99,5% das requisições com sucesso e p95 abaixo de 300 ms
  • Alarmes (os 4 sinais de ouro): 5xx no ALB, latência p95, CPU e memória das tarefas, hosts não saudáveis no target group
  • Metric filter contando erros nos logs
  • Banco: CPU, conexões e espaço livre do RDS
  • Custos: alarme de orçamento no Budgets
  • Notificação via SNS por e-mail ou Slack
  • Dashboard no CloudWatch, tudo criado pelo Terraform
Alarme bom é acionável: se dispara, alguém precisa fazer algo. Evite alarmes que todo mundo aprende a ignorar.

Etapa 5. Observabilidade · Tarefa 13

Teste de falhas

Prove que a operação funciona quebrando coisas de propósito, em dev.

Cenários

  1. Pare uma tarefa: o ECS repõe e o tráfego continua na outra AZ?
  2. Gere carga: o alarme de CPU dispara? O auto scaling reage?
  3. Force erros 500: o alarme de 5xx e o metric filter funcionam?
  4. Faça deploy de uma versão quebrada: o smoke test barra e o rollback acontece?
  5. Restaure o banco a partir de um snapshot
  6. Escreva um postmortem curto de um dos cenários
aws ecs stop-task --cluster dev --task TASK_ID hey -z 5m -c 50 https://dev.meu-app.com/ # gerador de carga aws rds restore-db-instance-from-db-snapshot ...

Documentação e entrega

README deve ter

  • Diagrama de arquitetura
  • Como rodar localmente e como fazer deploy
  • Explicação do pipeline e de cada verificação de segurança
  • SLOs, alarmes e o que fazer quando cada um dispara (runbook)
  • Custo mensal estimado
  • Decisões técnicas e lições aprendidas

Critérios de conclusão

  1. Infra criada do zero com terraform apply
  2. Commit na main chega à produção sem passos manuais
  3. Pipeline bloqueia vulnerabilidade crítica e segredo vazado
  4. Nenhuma credencial fixa no repositório ou no GitHub
  5. Alarmes testados e postmortem escrito
  6. terraform destroy ao final
