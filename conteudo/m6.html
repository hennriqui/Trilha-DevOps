Como usar

Módulo 6: infraestrutura como código

Segue o roadmap de Terraform do roadmap.sh: HCL, providers, recursos, variáveis, state, módulos, ambientes, CI/CD, testes e segurança. Você vai transformar a infraestrutura do módulo 4 em código.

  1. Instale o Terraform (ou OpenTofu) e configure a AWS CLI
  2. Abra os tópicos em ordem
  3. Rode plan antes de todo apply e leia o resultado com calma
  4. Ao final de cada sessão: terraform destroy

6A. Fundamentos · Tópico 1

IaC e o papel do Terraform

O que estudar

  • O que é IaC e os problemas do ClickOps (sem histórico, sem revisão, ambientes diferentes)
  • Declarativo vs imperativo
  • Provisionamento vs gerência de configuração: Terraform vs Ansible
  • Alternativas: CloudFormation, Pulumi, AWS CDK, OpenTofu (fork open source)
  • Como o Terraform funciona: código → providers → APIs, com state guardando o que existe
  • Idempotência e convergência
  • Licença BSL e OpenTofu (contexto do mercado)
Regra prática: depois que um recurso está no Terraform, mudanças só pelo código. Mexer no console gera drift.

HCL: sintaxe e expressões

O que estudar

  • Blocos: terraform, provider, resource, data, variable, output, locals, module
  • Argumentos e atributos e referências (aws_instance.web.id)
  • Tipos: string, number, bool, list, set, map, object, tuple
  • Interpolação "${}" e heredoc

  • Expressões for e splat [*]
  • Funções: lookup, merge, concat, cidrsubnet, file, templatefile, jsonencode

locals { azs = ["us-east-1a", "us-east-1b"] subnets = [for i, az in local.azs : cidrsubnet("10.0.0.0/16", 8, i + 1)] tags = merge(var.tags, { Ambiente = var.ambiente }) tipo = var.ambiente == "prod" ? "t3.small" : "t3.micro" } # terraform console > cidrsubnet("10.0.0.0/16", 8, 1) "10.0.1.0/24"

6A. Fundamentos · Tópico 3

Providers e versões

O que estudar

  • Providers: plugins que falam com as APIs (aws, cloudflare, github, random, tls)
  • required_providers e required_version
  • Restrições de versão: =, >=, ~> (pessimista)
  • Lock file .terraform.lock.hcl
  • Configuração do provider: região, default_tags, assume_role
  • Aliases para várias regiões ou contas
  • Autenticação: variáveis de ambiente, perfil, SSO, OIDC no CI
terraform { required_version = ">= 1.6" required_providers { aws = { source = "hashicorp/aws", version = "~> 5.0" } cloudflare = { source = "cloudflare/cloudflare", version = "~> 4.0" } } } provider "aws" { region = "us-east-1" default_tags { tags = { Projeto = "trilha-devops", Gerenciado = "terraform" } } } provider "aws" { alias = "virginia" region = "us-east-1" # certificados do CloudFront }

6B. Fluxo de trabalho · Tópico 4

init, fmt e validate

O que estudar

  • terraform init: baixa providers e módulos, configura o backend; -upgrade e -reconfigure
  • Estrutura de arquivos: main.tf, variables.tf, outputs.tf, providers.tf, versions.tf
  • terraform fmt (-recursive, -check no CI)
  • terraform validate
  • TFLint: erros que o validate não pega (tipo de instância inexistente)
  • O que versionar e o que ignorar no Git
terraform init terraform fmt -recursive terraform fmt -check # no CI terraform validate tflint --init && tflint # .gitignore .terraform/ *.tfstate *.tfstate.* *.tfvars # se tiver valores sensíveis

6B. Fluxo de trabalho · Tópico 5

plan, apply e o grafo

O que estudar

  • Como ler o plan: + criar, ~ alterar no lugar, - destruir, -/+ substituir
  • Por que algo é substituído: argumentos que forçam recriação
  • Plano salvo: plan -out e apply do arquivo
  • Grafo de dependências: implícitas por referência, explícitas com depends_on
  • Paralelismo e -target (só em emergência)
  • -replace para forçar recriação
  • lifecycle: create_before_destroy, prevent_destroy, ignore_changes
terraform plan -out=tfplan terraform show tfplan terraform apply tfplan terraform apply -replace=aws_instance.web terraform graph | dot -Tpng > grafo.png resource "aws_db_instance" "main" { lifecycle { prevent_destroy = true } }
Um -/+ num banco ou volume significa perda de dados. Pare e entenda o motivo antes de aplicar.

6B. Fluxo de trabalho · Tópico 6

destroy, import e drift

O que estudar

  • destroy total e com -target
  • Import: bloco import e geração de código com -generate-config-out
  • Drift: mudanças fora do Terraform, detectar com plan -refresh-only
  • Refatorar sem recriar: bloco moved e terraform state mv
  • removed: deixar de gerenciar sem destruir
  • Ferramentas: terraformer e former2 para importar infraestrutura existente
import { to = aws_s3_bucket.logs id = "meu-bucket-de-logs" } terraform plan -generate-config-out=gerado.tf terraform plan -refresh-only moved { from = aws_instance.web to = module.app.aws_instance.web }

6C. Organização · Tópico 7

Variables, outputs e locals

O que estudar

  • Variáveis: type, default, description, validation, sensitive, nullable
  • Precedência: -var, *.auto.tfvars, terraform.tfvars, TF_VAR_*, default
  • Outputs: expor IDs e endpoints, sensitive, terraform output -json
  • Locals: evitar repetição, nomes e tags padronizados
  • Tipos complexos: object e map(object) com optional()
variable "instancias" { type = map(object({ tipo = string disco = optional(number, 20) })) } variable "ambiente" { type = string validation { condition = contains(["dev", "staging", "prod"], var.ambiente) error_message = "Use dev, staging ou prod." } } output "alb_dns" { value = aws_lb.app.dns_name } export TF_VAR_ambiente=dev

6C. Organização · Tópico 8

Meta-argumentos e data

O que estudar

  • count e count.index, recursos condicionais (count = var.criar ? 1 : 0)
  • for_each com map ou set, each.key e each.value
  • Por que preferir for_each (remover item do meio não recria os outros)
  • dynamic blocks para regras de Security Group
  • depends_on explícito
  • Data sources: AMI mais recente, zonas, conta atual, recursos criados fora
  • Provisioners: por que evitar (prefira user data ou imagens prontas)
data "aws_availability_zones" "disp" { state = "available" } resource "aws_subnet" "publica" { for_each = toset(slice(data.aws_availability_zones.disp.names, 0, 2)) vpc_id = aws_vpc.main.id availability_zone = each.key cidr_block = cidrsubnet("10.0.0.0/16", 8, index(data.aws_availability_zones.disp.names, each.key) + 1) } dynamic "ingress" { for_each = var.portas content { from_port = ingress.value to_port = ingress.value protocol = "tcp" } }

6C. Organização · Tópico 9

Módulos

O que estudar

  • Root module vs child modules
  • Estrutura: main.tf, variables.tf, outputs.tf, README
  • Fontes: caminho local, Git com ref, Terraform Registry com versão
  • Design: interfaces pequenas, sem provider dentro do módulo, outputs úteis
  • Módulos da comunidade: terraform-aws-modules (vpc, ec2, rds, alb)
  • Composição: um módulo de ambiente chamando vpc, app e dados
  • Documentação automática com terraform-docs
infra/ ├─ modules/ │ ├─ network/ (VPC, subnets, rotas) │ ├─ app/ (ALB, EC2 ou ECS, SGs) │ └─ data/ (RDS, secrets) └─ envs/ ├─ dev/main.tf └─ prod/main.tf module "network" { source = "../../modules/network" cidr = "10.0.0.0/16" ambiente = "prod" } module "app" { source = "../../modules/app" vpc_id = module.network.vpc_id subnet_ids = module.network.private_subnet_ids }

6D. State e escala · Tópico 10

O arquivo de state

O que estudar

  • Para que serve: mapear código para recursos reais, guardar metadados e dependências, performance
  • Formato JSON e por que nunca editar à mão
  • Comandos: state list, show, mv, rm, pull, push
  • Dados sensíveis em texto puro no state
  • Refresh e reconciliação com a realidade
  • Recuperação: versionamento do bucket para voltar uma versão
terraform state list terraform state show module.app.aws_lb.this terraform state mv aws_instance.web aws_instance.api terraform state rm aws_s3_bucket.legado terraform state pull > backup.tfstate
O state pode conter senhas de banco e chaves. Trate o arquivo como um segredo.

6D. State e escala · Tópico 11

Backend remoto e lock

O que estudar

  • Backend local vs remoto
  • Backend S3: bucket versionado e criptografado, key por ambiente
  • Lock: use_lockfile no S3 (versões recentes) ou tabela DynamoDB (forma antiga)
  • Bootstrap: criar o bucket do state à parte
  • Migrar state: init -migrate-state
  • Ler outputs de outro state: terraform_remote_state
  • HCP Terraform (Terraform Cloud) como alternativa gerenciada
terraform { backend "s3" { bucket = "trilha-tfstate-123456789012" key = "prod/app.tfstate" region = "us-east-1" encrypt = true use_lockfile = true } } terraform init -migrate-state terraform force-unlock LOCK_ID # só se o lock travou

Ambientes, CI e testes

O que estudar

  • Separar ambientes: pastas por ambiente (recomendado) vs workspaces
  • Terragrunt para reduzir repetição (conceito)

# tests/rede.tftest.hcl run "subnets_criadas" { command = plan assert { condition = length(module.network.private_subnet_ids) == 2 error_message = "Esperava 2 subnets privadas" } } terraform test infracost breakdown --path .

DevSecOps

IaC seguro

O que estudar e aplicar

  1. State protegido: bucket privado, criptografado com KMS, versionado e com acesso restrito
  2. Sem segredos no código: sensitive = true, valores vindos do Secrets Manager via data source, ou gerados com random_password
  3. Scanners de IaC: Checkov, Trivy config, tfsec (agora no Trivy)
  4. Policy as code: OPA/Conftest ou Sentinel para regras da empresa
  5. Permissões do CI: role de plan só leitura, role de apply separada e com aprovação
  6. Versões fixadas de providers e módulos, lock file versionado
  7. Padrões seguros nos módulos: criptografia ligada, sem acesso público, logs ativos
checkov -d infra/ --framework terraform trivy config --severity HIGH,CRITICAL infra/ conftest test tfplan.json -p policy/ resource "random_password" "db" { length = 32 }

Projeto prático

A infraestrutura do módulo 4 em código

  1. Bootstrap: bucket do state criado com Terraform numa pasta à parte
  2. Módulos network, app e data com README gerado pelo terraform-docs
  3. Ambientes dev e prod em pastas separadas, cada um com seu state
  4. Senha do banco gerada com random_password e guardada no Secrets Manager
  5. Opcional: registros DNS na Cloudflare pelo provider cloudflare
  6. Pipeline: fmt, validate, tflint, Checkov e plan no PR; apply com aprovação após merge, via OIDC
  7. Um terraform test validando a rede
  8. Prova final: destroy e apply de novo, tudo volta igual
